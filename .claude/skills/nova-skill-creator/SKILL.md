# nova-skill-creator — 스킬 만들기 · 고치기

이름에 `nova-` 를 붙인 까닭: 전역에 일반 스킬 작성 스킬(skill-creator)이 있어, Nova 규칙이 붙은 이 스킬과 발동이 헷갈리지 않게 하려는 것이다.

정본은 아래이고, 이 스킬과 다르면 정본이 옳다.
- 3층 결정: [ADR-009](../../../docs/adr/ADR-009-commands-skills-agents.md) — "스킬은 값을 갖지 않는다"
- 형식 검사 규칙(S1~): `scripts/claude_check.py` 머리말 — **규칙을 이 스킬에 베끼지 않는다**
- 방법: `superpowers:writing-skills` · 지도 [superpowers.md](../../../docs/conventions/superpowers.md) §2 '개선' 행 · §2.1
- 좋은 예: [nova-screen](../nova-screen/SKILL.md)(정본을 가리키는 머리 · 번호 절 · 출구 표 · references 분리)

모든 문장(description · 본문 · references)은 **한국어**다([CLAUDE.md](../../../CLAUDE.md) 규칙 0). 한글이 없는 md 는 검사에서 실패한다.

## 0. 만들기 전 세 가지 — 하나라도 "아니오"면 만들지 않는다
1. 같은 판단 묶음이 **두 번 이상, 서로 다른 요청 · 명령**에서 필요했는가
2. 기존 스킬 · 명령 · 에이전트를 조금 넓혀서는 안 되는가 — `.claude/skills/` 의 description 과 CLAUDE.md 명령 표를 실제로 읽고 대조한다
3. 발동할 자리가 있는가 — 사용자가 실제로 쓰는 요청 문장 2~3개를 지금 적을 수 있는가

## 1. 스킬인가, 명령인가, 에이전트인가 (ADR-009 3층)
| 이런 것이면 | 층 | 위치 | 만드는 법 |
|---|---|---|---|
| 순서 · **승인 관문** · 멈춤이 있는 절차, 사용자가 `/이름` 으로 부른다 | 명령 | `.claude/commands/<이름>.md` | nova-command-creator |
| 요청 문장으로 **자동 발동**되는 판단 묶음(어떤 템플릿 · 어떤 순서 · 어디로 빠지나) | 스킬 | `.claude/skills/<이름>/SKILL.md` | 이 스킬 |
| 명령이 정한 자리에서 부르는 **역할**(도구 권한 경계가 필요) | 에이전트 | `.claude/agents/<폴더>/<이름>.md` | nova-subagent-creator |
| 판정 · 기록의 기계 부분 | 도구 | `scripts/*.py` → `python nova.py …` | 계획 · task 로 구현 |
- 관문이 있는 일을 스킬로 만들지 않는다 — 자동 발동은 관문을 건너뛰게 만든다
- 둘 다 필요하면 명령이 절차를, 스킬이 그 안의 판단을 맡고 명령이 스킬 이름을 부른다

## 2. 폴더 · frontmatter
```text
.claude/skills/<이름>/
├── SKILL.md          필수 — frontmatter + 짧은 본문
└── references/       선택 — 필요할 때만 읽는 자세한 것(틀 · 판단 기준 · 예시)
```
- `name` — 폴더 이름과 같다. 전역 스킬과 겹치는 이름이면 `nova-` 를 붙인다
- `description` — 한국어. **발동 장치**다: 무엇을 하는지 + 따옴표로 실제 요청 문장 3~5개 + 끝내는 지점 + "…는 여기가 아니다(어디 몫)" 경계. 본문은 발동 뒤에야 읽히므로 '언제'는 반드시 여기에
- `canon: design-system` — 화면 · 토큰 · 부품을 다루는 스킬이면 붙인다. 붙이면 색 · px · 비율 리터럴이 검사에서 실패한다(인용이 꼭 필요하면 같은 줄에 검사기가 정한 허용 표지)
- 그 밖의 키(허용 도구 · 모델 등)는 넣지 않는다 — Nova 스킬은 쓰지 않고, 검사기 · 동작이 확인되지 않았다
- 실행 스크립트를 스킬 폴더에 두지 않는다 — 기계 부분은 `scripts/` 도구 + `python nova.py` 로(테스트 · lint 를 받게)

## 3. 본문 — 짧게, 정본을 가리켜서 (점진 공개)
읽히는 순서는 셋이다: ① name + description(늘 컨텍스트에) → ② SKILL.md 본문(발동했을 때) → ③ references(본문이 가리킬 때만). 그래서
- **SKILL.md 는 500줄 이하**, 실제로는 한두 화면이 좋다. 넘치면 references 로 뺀다
- 머리에 "이 스킬은 값을 갖지 않는다 — 정본은 …" 와 정본 목록(규약 · 토큰 · README · ADR)
- 번호 절로 순서를 준다: 조회 먼저 → 고르기 → 하기 → 확인 → 출구(없는 것이 필요할 때 어디로 가나)
- Claude 가 이미 아는 일반 지식은 쓰지 않는다 — 이 저장소에만 있는 판단 · 경로 · 함정만
- 자유도를 일의 위험에 맞춘다: 되돌릴 수 있는 일은 원칙만, 되돌리기 어려운 일(계약 · DB · 공개)은 정확한 단계와 멈춤
- 값 · 개수 · 임계 · 판본 번호를 적지 않는다 — 정본이 바뀌면 스킬이 거짓이 된다
- 상대 링크 · 백틱 안 저장소 경로는 실재해야 한다(자리표시 `<…>` · `YYMMDD` 는 검사에서 뺀다)
- 에이전트를 부르면 백틱 이름으로 쓴다 — 검사기는 스킬 본문의 백틱 이름도 에이전트 호출로 세므로, 없는 에이전트처럼 생긴 이름을 백틱에 넣지 않는다
- 빈 틀: [references/template.md](references/template.md)

## 4. 시험 — 압박 시나리오 (`superpowers:writing-skills`)
쓰기 전에 실패를 먼저 본다: 스킬 없이 그 요청을 처리하면 무엇을 놓치는지 한 줄로 적고, 스킬이 그것을 막는지 확인한다.
- **발동** — 예시 요청 2~3개(description 의 따옴표 문장과 다른 말투로도 하나): 발동하는가
- **경계** — 이웃 스킬 · 명령과 헷갈리는 요청 하나: 경계 문장이 맞는 곳으로 보내는가(예: 화면 스킬에 "버튼 색만 바꿔줘" → 토큰 원천)
- **압박** — "급하니 확인 건너뛰고" 같은 요청 하나: 스킬의 확인 단계 · 출구가 그래도 지켜지는가
- 결과를 보고에 한 줄씩 적는다. 발동이 안 되면 본문이 아니라 description 을 고친다

## 5. 연결 · 검증 · 기록
- superpowers.md §2.1 표에 한 줄(어느 단계에서 쓰는 스킬인가), 스킬을 부르는 명령이 있으면 그 단계에 스킬 이름 — 다른 담당 소관이면 "넣을 연결"(파일 · 문장 초안)로 main 에 보고한다
- 새 프로젝트는 `.claude/` 를 통째로 물려받고 복제본은 `/sync-upstream` 으로 받는다 — 특정 프로젝트 전용 스킬이면 이름 · 경로에 그 프로젝트를 밝힌다
```bash
uv run python scripts/claude_check.py --check
uv run python scripts/docs_index.py --check
python nova.py lint
```
- 증거 없이 "됐다"고 하지 않는다 — 출력의 오류 수를 보고에 붙인다
- 3층 체계 자체를 바꾸는 일(새 층 · 발동 규칙 · 검사 규칙 변경)은 되돌리기 어려운 체계 변경 → REQ · ADR, 번호가 붙는 기록은 main 만 쓴다. 스킬 하나 추가는 작업 단위 이력(`/history-new`)으로 충분하다
