# /masterplan — 통합 설계 판본

인자: `$ARGUMENTS`
규칙: [docs/plans/README.md](../../docs/plans/README.md) §1(판본 · 채택 · 봉인) · §5(목표 · 종료 조건 · 하지 않는 것) · §6(병렬 · 공통 영역) · 결정 [ADR-008](../../docs/adr/ADR-008-parallel-bus-release.md)
초안 쓰는 절차의 정본: **nova-masterplan 스킬**(이 명령은 진입 분기 · 관문 · 마무리를 맡고, 초안 작성은 스킬을 부른다)

> **두 층 계획** — 마스터플랜(이 명령, `docs/plans/master_plan.md`)은 *전체 그림과 로드맵*, `/plan-new`(`docs/plans/plan_REQ_NN.md`)는 *요구 하나의 단계별 상세 설계*다. 마스터플랜에 구현 코드 · 화면 상세 · 칸 수준 ERD 를 넣지 않는다.

## 0. 진입 분기 — 정본이 있으면 덮어쓰지 않는다
먼저 `python nova.py masterplan status` 로 지금 정본 · 이력 · 열린 초안을 본다.

| 상태 | 무엇을 하나 |
|---|---|
| 시작 초안(v0.1 — new-project · 템플릿 초기화 직후) | **최초 작성** — 아래 절차로 `drafts/master_plan_v1.0-draft.md` 를 쓰고 채택한다 |
| 정본 있음 · 이번 일이 **기존 계획에 요구 하나를 더하는 것** | **편입** — `/plan-new` 7단계(마스터플랜 §5 에 계획 한 줄 추가 초안 → 채택). 자문(2단계)은 면제 |
| 정본 있음 · **새 마일스톤 · 별개의 큰 계획** | **새 판본** — 지금 정본을 초안으로 복사해 고친다(`drafts/master_plan_v<다음>-draft.md`). 정본은 채택 때까지 그대로 |
| 열린 초안이 이미 있음 | 그 초안을 이어서 고친다(초안은 하나만 — 둘이면 어느 것이 다음 판본인지 갈린다) |

🔴 **정본(`master_plan.md`)을 직접 고치지 않는다.** 정본에 반영되는 유일한 길은 `masterplan adopt` 다(봉인 해시 · lint 가 지킨다). 덮어쓰기를 반복하면 "처음에 무엇을 계획했나"에 답할 수 없게 된다.

## 1. 입력 관문
- 북극성 `docs/PROJECT.md` 가 있어야 한다(없으면 템플릿 `docs/_template_PROJECT.md` 로 먼저 — `/kickoff`)
- **기반 결정**(`docs/product/spec.json` 의 `foundation` 또는 해당 ADR)이 있어야 한다 — 없으면 `/foundation` 을 먼저 권고한다(아키텍처가 모듈 지도 · 배포 토폴로지를 좌우한다). 기존 Nova 기본 스택을 그대로 쓰면 "Nova 기본(ADR-001)"을 근거로 적는다
- 함께 읽는다: `docs/product/prd.json` · `spec.json`(있으면) · 열린 요구 `docs/requirement/requirement_index.md` · 대장 `docs/registry/*.md` · 판본 `python nova.py release status` · 진척 `python nova.py progress`
- **위임**: 입고 자료가 많으면 `inbound-analyst`(글) · `mockup-analyst`(목업 · 캡처)를 파일마다 한 메시지에 함께 띄워 요약을 받는다. 긴 본문 초안은 `masterplanner` 에이전트에 맡길 수 있다(판단 · 승인 요청은 main)
- 경량 일(요구 하나 · 작은 변경)은 이 명령을 생략하고 바로 `/plan-new`

## 2. 자문 — 지도를 그리기 전에 (`practice-advisor`)
입력을 읽은 **뒤**, 지도를 그리기 **전**에 `practice-advisor` 에이전트에게 맡긴다. 마스터플랜은 숲이라, 여기서 놓친 모듈은 요구 단위로 내려가서는 발견되지 않는다(어느 요구도 그것을 가리키지 않으므로).

| 받는 것 | 처분 |
|---|---|
| ⓐ 의뢰 충실도 | 로드맵에 반영 |
| ⓑ 놓친 관점(운영 · 권한 · 감사 · 마이그레이션 · 삭제/보존 · 장애 · 한국 규제) | **채택하든 안 하든 이름으로 남긴다** — 넣으면 해당 절, 안 넣으면 '하지 않는 것' 또는 '위험'에 이유와 함께 |
| ⓒ 기회 | **지도에 넣지 않는다** — `/req-new` 후보로 따로 적고, 채택되면 다음 판본의 편입 후보 |

⚠ **범위를 조용히 넓히지 않는다** — 사용자가 요청한 것과 자문이 더한 것을 문서에서 갈라 적어, 사람이 그 차이를 판단할 수 있게 한다.

## 3. 초안 — nova-masterplan 스킬 §3
`docs/plans/drafts/master_plan_v<X.Y>-draft.md` 에 쓴다(머리 표 상태 `초안`). 블록:
1. **한 줄 요약**(북극성 연결) · 목표
2. **모듈 지도** — 서비스 · 공통 영역 · 도메인 팩, 소유(서비스는 자기 DB 만) — 표로
3. **요구 로드맵** — 요구 ↔ 모듈 · 마일스톤 · 우선순위 표, 각 요구는 이후 `/plan-new` 로 상세화한다고 적는다(하향 연결)
4. **의존 그래프**(mermaid)
5. **횡단 관심사** — 정본은 기반 결정(spec.json foundation · ADR)이고 여기서는 요구 영향 · 방침만 가리킨다(중복 선언 금지)
6. **큰 그림 데이터 모델**(전체 ERD — 칸 수준은 각 계획으로)
7. **마일스톤** — **M0 은 걷는 골격(Walking Skeleton)으로 고정**: CI · DB · 인증 한 경로 · 화면 셸 하나가 끝에서 끝까지(Nova 로 만든 프로젝트는 템플릿 초기화로 대부분 이미 녹색 — 무엇이 남았나만 적는다). 기능 요구는 M1 부터
8. **위험 · 마이그레이션 · 되돌리기**
9. **종료 조건**(1~7개 · 소진형 금지 — `goals.py` 형식) · **하지 않는 것** · **공통 영역 완료 선언**(증거 칸) · **병렬 묶음**(경로 글롭 겹침 금지 — 설계는 `orchestrator`)
- 도메인 팩을 쓰는 프로젝트면 **도메인 채택 표**(팩 · 확장 서비스 · 쓰지 않는 팩은 이유) — [STD-DOMAIN-PACK-001](../../docs/std/STD-DOMAIN-PACK-001.md)
- 모듈 분해 · 의존 · 마일스톤은 **표 · 그림으로**(산문 나열 금지)

## 4. 점검 → 결정 → 채택
1. `python nova.py masterplan check`(초안이 '정식'이 아닌지 · 봉인 그대로인지)
2. 묶음 표를 넣었으면 `python nova.py parallel-gate` — 나중에 `/worktree-new` 가 막을 것(경로 겹침 · 공통 영역 미완)을 지금 알린다(막지는 않는다)
3. 사용자에게 모듈 지도 · 로드맵 요지 · 자문이 더한 것(갈라서) · 대가를 보이고 **결정을 받는다**(되돌리기 어려운 결정 — SOUL 되돌림 원칙)
4. `python nova.py masterplan adopt docs/plans/drafts/<초안> --why "<근거 요구 · 사용자 결정>" --what "<바뀐 것>"` — 지난 판본 봉인 · 이력 · 초안 삭제
5. `/docs-write` → `/git-save`

## 마무리
- 채택한 판본의 모듈 지도 · 로드맵 요지를 보고하고, **첫 마일스톤의 요구마다 `/plan-new` 를 제안**한다
- 릴리스 판본과 잇는다: 첫 마일스톤을 판본으로 내려면 `/release`(draft — 묶인 요구 · 종료 조건)

## 하지 않는 것
- 정본 · 봉인본 직접 고치기 · 사용자 결정 없이 채택 · 초안을 둘 열기
- 자문이 더한 범위를 요청과 섞어 적기 · 끝이 없는 종료 조건("빠짐없이 · 전부")
- 마스터플랜에 구현 코드 · 화면 상세 · 칸 수준 ERD 넣기(그것은 `/plan-new`)
