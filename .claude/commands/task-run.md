규칙: [docs/conventions/superpowers.md §5](../../docs/conventions/superpowers.md)

## 절차

1. 계획 `docs/plans/plan_REQ_NN.md`(특히 §11.1 전역 제약 · §11.2 검토 초점)와 `docs/plans/tasks/tasks_REQ_NN.md` 를 읽는다. 요구가 승인되지 않았으면 멈추고 `/req-analyze` 로 돌아간다
2. **실행 방식**: 인자에 없으면 사용자에게 묻는다(추천 1개 + 이유 한 문장)
   - `subagent` → `superpowers:subagent-driven-development`: task 마다 새 구현자(아래 '경로 → 구현자' 표의 에이전트) + 새 검토자(`code-reviewer` 에이전트), 마지막에 전체 검토. 꼼꼼하지만 비싸다. 에이전트는 커밋 · 기록을 하지 않는다 — 커밋 · `git_record.py` 는 main
   - `native` → `superpowers:executing-plans`: 이 세션에서 직접 구현, 마지막에 새 검토자 한 번. 빠르다
2-0. **검토 무게는 위험에 비례**(REQ-261105-10-3) — `subagent` 의 'task 마다 새 검토자'를 task 성격으로 조절한다. 모델 이름은 `.claude/agents/README.md` '모델 등급' 표를 따른다
   | task 성격 | 검토 | 고치기 뒤 재검토 |
   |---|---|---|
   | 문서 · 규약 · 기계적 수정(한 단계 안 여러 task) | **단계 묶음 검토 한 번**(중간 등급) | 지적이 있을 때만, 범위를 좁혀 |
   | 보통 코드(스크립트 · 화면 · 서비스 로직) | task(또는 같은 파일 묶음)마다 검토(중간 등급) | 범위를 좁혀(중간 등급) |
   | [DEEP] — 인증 · 권한 · 계약 · DB 구조 · 동시성 · 금액 · 운영 설정 | task 마다 상위 등급 검토 + 해당 판정자(`security-auditor` · `contract-auditor`) | 범위를 좁혀(상위 등급) |
   | 최종 | 계획 끝에 브랜치 전체 검토 한 번(상위 등급) | 고치기 한 번에 모아 |
   - 이 표는 검토를 **빼는** 근거가 아니다 — 문서 task 도 단계 끝 묶음 검토는 한다. 무게를 낮춘 판단은 원장에 `Ruling:` 으로 남긴다
2-1. **경로 → 구현자**(task 가 건드리는 경로로 하나를 고른다)

3. **격리**(선택): 여러 단계짜리 작업이면 `superpowers:using-git-worktrees` 로 작업 폴더를 따로 만들고 브랜치 `feat/plan_REQ_NN-<요약>`([git.md](../../docs/conventions/git.md))
4. task 마다 `superpowers:test-driven-development` 다섯 단계: 실패 테스트 작성 → 실패 확인 → 최소 구현 → 통과 확인 → 커밋(**그 테스트 하나**만 돌린다 — 몇 초. 커밋은 단계 관문에서 묶어도 된다)

   - 커밋 메시지는 `feat(범위): 한국어 요약`. git 기록은 **푸시 묶음마다** 한 번 `uv run python scripts/git_record.py "<요약>"`(지난 기록 이후 커밋 전부)
   - 새 표 · 칸 · API · 토픽 · 권한 이름을 만들기 직전에 `registry-keeper` 에이전트로 원장을 조회한다
   - 화면 task 는 `nova-screen` 스킬(조립) · 문구는 `ux-writer` 에이전트 · 확인은 `nova-ui-verify` 스킬(`e2e-tester` 에이전트 — `python nova.py ui-smoke`)을, 생성물은 `registry.py sync` · `ledgers.py` 를 넣는다
   - 표 · 칸 · API 를 **만들기 직전에** 대장을 다시 조회한다(`python nova.py impact <이름>`) — 계획 뒤에 생긴 것과 겹치지 않게
5. 끝난 task 는 **명령 출력으로 확인한 뒤**(task 마다는 빠른 검사 `python nova.py quick` — 바뀐 파일에 닿는 테스트 · 검사만. **단계 끝 · 푸시 묶음 · [DEEP] task** 는 전체 `python nova.py check` — test · lint 를 함께, 필요하면 `tester` 에이전트, lint 축이 길면 `verifier`) `- [x]`(superpowers:verification-before-completion) — 커밋과 같은 흐름에서 바로 표시한다. 하다 생긴 일은 🆕 로 추가하고 같은 줄에 판정(`지금 — <깨는 종료 조건>` / `다음 판본`)을 적는다(plans README §5)
5-0. **단계 관문** — 단계의 마지막 task 뒤에 한 번: `python nova.py quick --stage T<NN>-<단계>`(그 단계 task 에 적힌 테스트 + 바뀐 파일에 닿는 테스트 · lint 를 pytest 한 번으로) → 전체 `python nova.py check`(test 묶음은 동시에 돈다) → 커밋 묶음 · 푸시 · git 기록. 관문이 실패하면 그 단계 task 체크를 풀고 고친다
5-1. 팩(`packs/<팩>/`)이나 팩이 확장하는 서비스를 바꾼 task 는 검토 때 `<팩>-specialist`(팩 이름의 `_` 는 `-`) 에이전트로 용어 · 규칙을 확인한다
6. 서로 무관한 task 가 2개 이상이면 `superpowers:dispatching-parallel-agents` 로 나눠도 된다(같은 파일을 건드리면 안 된다)
7. 막히면 추측으로 고치지 말고 `/debug`(`debugger` 에이전트). 계획과 다르게 가야 하면 멈추고 사용자에게 묻는다(계획 §12.1 실측 정정에 남김)
7-1. **멈춤 조건** — 아래 중 하나면 다음 task 로 가지 않고 멈춘다(자동으로 넘지 않는다)
   | 조건 | 다음 |
   |---|---|
   | 계획 §범위 밖 파일을 고쳐야 한다 | 사용자 확인 또는 `/change` |
   | 게이트(test · lint)가 빨강 | 원인부터 — **다시 돌려 초록을 만들지 않는다** |
   | 실패 테스트(RED)를 못 만든다 | 계획 · 수용 기준을 다시 본다 |
   | 판단 포인트가 미결(계획 §11 · 요구 미결 질문) | 사용자에게 묻는다 |
   | 푸시 · 태그 · 외부 공개 · 되돌리기 어려운 변경 | 사용자 확인(SOUL 되돌림 원칙) |
   | 종료 조건이 모두 녹색(`python nova.py exit-check REQ-…`) | 끝 — 새로 보인 것은 새 요구로 |
   | 사람 판단 포인트 모음(`--auto` 에서 위 판단 · 확인 조건이 쌓임) | 한 번에 모아 묻는다 — 아래 '질문 모으기' |
8. 모든 task 가 끝나면 전체 검토(`/review-request`) → `/finish`

## 자동 진행(`--auto`)
`--auto` 일 때만 쓴다. main 세션이 운전자가 되어 겹치지 않는 task 를 **한 층으로** 구현자에게 직접 배치한다(구현자 · 검토자가 다른 에이전트를 부르지 않는다). 판정은 계속 main 이 한다. 인자 `[T<NN>-<단계>.<순번>부터]` 는 `--auto` 에서 쓰지 않는다 — 어디서 이어 갈지는 tasks 의 체크가 정한다('재개').

### 시작 전 점검
1. **브랜치**: `git branch --show-current` 가 `feat/` 로 시작하지 않으면 시작하지 않고 안내한다(절차 3 으로 격리 브랜치부터)
2. **깨끗한 트리**: `git status --porcelain` 에 미커밋 변경이 있으면 시작하지 않고 멈춤 조건으로 올린다 — 반쯤 된 task 일 수 있으니 이어 갈지 · 버릴지는 사람이 정한다
3. **원장**: `.superpowers/sdd/<tasks 이름>/progress.md` 가 없으면 첫 줄에 `BASE <커밋> · 시작 브랜치 <이름> · 시각` 을 적는다(원장은 커밋하지 않는다). 있으면 첫 줄은 그대로 두고 `재개 <시각> · HEAD <커밋>` 줄만 덧붙인다 — 원장이 없는데 이미 `--auto` 를 하던 중이면 BASE 를 추측하지 말고 질문 모음에 올린다

### 자동 진행 고리
1. **다음 묶음 고르기**: `uv run python scripts/task_batch.py docs/plans/tasks/tasks_REQ_NN.md --max N [--skip ID,…]` 을 돌린다(N 은 '안전장치' 표의 동시 구현자 수). 질문 모음에 올린 task 는 `--skip` 으로 뺀다. 종료 코드로 가른다(0 은 출력 문구로 두 뜻을 가른다) — 정본은 스크립트 머리 설명이다
   | 종료 · 출력 | 다음 |
   |---|---|
   | 0 · `다음 묶음 …` | 2번으로 |
   | 0 · `끝 — 열린 task 없음` | 계획 완료 — 절차 8(`/review-request` → `/finish`)로 |
   | 2 · 막힘(선행이 끝나지 않음) | 멈춤 — 질문 모음에 올린다(무한 대기 금지) |
   | 3 · 형식 이상(stderr 의 줄 번호) | 멈춤 — tasks 줄을 고칠지 질문 모음에 올린다 |
   | 4 · 대기(`--skip` 한 task 만 남음) | 질문 모음을 보내고 답을 기다린다 |
   | 1 · 파일 없음 · 인자 오류 | 인자부터 바로잡는다 |
2. **사람 관문 선별**: 묶음의 task 줄에 `[DEEP]` 이 있거나 `파일:` 경로가 아래 구현자 금지 파일에 닿으면 배치하지 않는다 — 질문 모음에 올리고 `--skip` 에 더해 1번을 다시 돌린다
3. **구현자 배치**: 묶음의 task 마다 절차 2-1 표로 구현자를 고르고 '병렬 배치'대로 **배경으로 동시에** 부른다. 지시에는 task 원문 · 끝난 기준 · 한국어 4절 보고 요구와 함께 다음을 넣는다
   - 지시서의 `파일:` 경로만 고친다 — 그 밖을 고쳐야 하면 고치지 말고 멈춰 보고한다
   - **커밋 · 푸시 금지**(`--auto` 의 구현자는 커밋하지 않는다 — 절차 4 의 커밋 · 기록은 main) · 전체 `test` · `check` 금지(절차 4)
   - 의존성(`pyproject.toml` · `uv.lock` · `package.json` · `package-lock.json`) · `.claude/settings.json` · `rbac.json` · 권한 변경 금지 — 필요하면 보고
4. **task 검토 고리**: 묶음의 구현자가 모두 돌아오면 task 마다 새 검토자(`code-reviewer` 에이전트)로 검토한다(절차 2 `subagent`). 같은 트리에 다른 task 의 변경이 섞여 있으므로 검토 대상은 그 task 의 경로로 좁힌다(`git diff -- <경로…>`). 치명 · 중요는 같은 구현자 역할로 고치기를 보내고 다시 검토한다 — 고치기 회차는 '안전장치' 표 안에서만
5. **main 재확인**: 구현자 · 검토자의 "통과"를 믿지 않는다. main 이 그 task 의 테스트 · `python nova.py quick` 을 직접 돌려 출력을 본다(절차 5). 바뀐 파일 비교도 그 task 의 경로로 좁혀 본다
6. **체크 · 커밋**: 재확인이 초록이면 `- [x]` 로 표시하고 **그 task 의 경로(와 tasks 파일)만 밝혀** `git add <경로…>` 뒤 커밋한다 — `git add -A` · `git commit -a` 금지, `--auto` 는 task 마다 커밋한다(절차 4 의 "단계 관문에서 묶어도 된다"는 쓰지 않는다). 커밋 전 `git status --porcelain` 의 변경이 모두 허용 경로 안인지 본다 — 허용 경로 = 이번 묶음 task 들의 `파일:` 경로 + 그 tasks 파일(원장 폴더는 git 이 무시해 잡히지 않는다). 그 밖의 변경이 있으면 구현자가 범위를 넘은 것이니 멈춤 조건으로 올린다. 보류한 task 의 변경은 아래 '보류 처리'로 이미 트리에서 치워 두므로 이 검사에 걸리지 않는다(커밋 · 체크는 main 만 — 단일 기록자)
7. **단계 관문**: 단계의 마지막 task 를 체크했으면 절차 5-0 의 `python nova.py quick --stage T<NN>-<단계>` → 전체 `python nova.py check` 까지만 한다 — **푸시 · git 기록은 하지 않고** 질문 모음에 '푸시 묶음'으로 올린다. 관문이 빨강이면 5-0 의 "체크를 풀고 고친다"가 아니라 절차 7-1 대로 멈춘다(원인부터). 전체 `check` 가 도는 동안은 '안전장치'의 관문 중 부하 규칙을 지킨다
8. **반복**: 1번으로 돌아간다. 멈춤 조건(절차 7-1 표 · '안전장치' 상한)에 걸리면 반복을 끝내고 보고한다

### 보류 처리
task 를 보류(실패 · 사람 판단 대기)할 때 main 이 그 task 의 변경을 트리에서 치워, 독립 task 의 커밋 전 검사가 막히지 않게 한다. 보류한 task 는 이 순서로 처리한다
1. **패치 저장**: 새 파일이 있으면 먼저 `git add -N <새 파일…>` 한 뒤 `git diff -- <파일: 경로…> > .superpowers/sdd/<계획>/held-<ID>.patch`
2. **그 경로만 되돌리기**: 추적 파일은 `git restore -- <경로…>`, 새 파일은 `git restore --staged -- <새 파일…>` 뒤 삭제 — 다른 task 의 경로는 건드리지 않는다
3. **원장에 한 줄**: `보류 <ID> · 패치 <경로> · 사유`. 질문 모음에 올리고 `--skip` 에 더한다
4. **다시 열 때**: 사람이 이어 가기로 하면 `git apply <패치>` 로 변경을 되살린 뒤 `--skip` 에서 뺀다(패치가 안 맞으면 사람 판단)

### 병렬 배치
- `task_batch.py` 가 낸 묶음만 동시에 부른다 — **한 메시지에 구현자 호출을 함께**(배경으로) 담는다(묶음이 1개면 1개). 같은 작업 트리에서 파일만 분리해 돌린다(worktree 를 따로 만들지 않는다)
- 묶음에 없는 task 는 앞 묶음이 체크된 뒤 다시 `task_batch.py` 를 돌려 차례로 한다. 겹침을 손으로 다시 판정해 묶음을 넓히지 않는다 — 의심스러우면 겹침(혼자 한 묶음)이 스크립트의 원칙이다
- 겹침 판정 — 같은 경로이거나 한쪽이 다른 쪽의 폴더이면 겹침, 경로가 없는 task 는 모두와 겹침
  | 두 task 가 적은 경로 | 판정 |
  |---|---|
  | `services/sample/` 와 `services/sample/items.py` | 겹침 — 폴더 안팎이라 차례로 |
  | 둘 다 `tests/test_y.py` 를 가리킴 | 겹침 — 같은 테스트 파일을 가리키면 차례로(묶음이 1개씩만 나오는 것은 정상) |
  | `scripts/*.py` 와 `scripts/task_batch.py` | 겹침 — 글롭은 앞 폴더 전체로 본다 |
  | `a/b.py` 와 `a/bc.py` | 안 겹침 — 이름이 비슷할 뿐 다른 파일이라 동시에 |
  | `scripts/task_batch.py` 와 `.claude/commands/task-run.md` | 안 겹침 — 동시에 |
- 동시 호출 수는 `--max` 에 '안전장치' 표의 동시 구현자 수를 넣는다(숫자를 여기 따로 적지 않는다)

### 질문 모으기
- **질문은 main 만 한다** — 하위 에이전트에서는 사용자 질문 도구가 늘 빠진다. 구현자 · 검토자가 사용자 판단이 필요하다고 보고하면 main 이 받아 모은다
- 질문 모음에 쌓는 것: 절차 7-1 의 범위 밖 파일 · 판단 포인트 미결 · 푸시 · 태그 · 되돌리기 어려운 변경, 위 고리의 막힘 · 형식 이상 · 대기, `[DEEP]` · 의존성 추가 · 권한 확대, 실패해 보류한 task, 푸시 묶음. 그때그때 묻지 않고 한 번에 모아 묻는다(선택지마다 추천 1개 + 대가 한 줄). **게이트 빨강은 쌓지 않는다** — 절차 7-1 대로 바로 멈춘다
- 질문 모음에 올린 task 는 `--skip` 으로 빼고, 그와 **독립인 task**(`task_batch.py` 가 계속 묶음으로 내는 것)는 기다리는 동안 계속 진행한다. 종료 4(대기)나 묶음이 없으면 질문을 보내고 멈춘다
- **푸시는 모아서 묻는다** — 단계마다 묻지 않고, 푸시 묶음이 쌓였거나 멈출 때 커밋 목록과 함께 한 번에 묻는다. 사용자가 승인하기 전에는 푸시 · `git_record.py` 를 하지 않는다

### 안전장치
| 상한 | 값 |
|---|---|
| task 당 고치기 회차 | 5 |
| 한 번의 `--auto` 실행당 하위 에이전트 호출 수 | 20 |
| 연속 실패 task 수 | 2 |
| 동시 구현자 수 | 3 |
- 값은 사용자 승인(2026-11-05)을 받은 것이다. 이 표가 값이 적힌 유일한 곳이다 — 다른 문서에는 숫자를 옮기지 않고 이 표를 가리킨다
- **세는 것(main 이 원장에)**: 고치기 회차는 task 마다, 호출 수는 구현자 · 검토자 · 재검토자 · `debugger` · 배경 조사 · 자문까지 하위 에이전트를 부를 때마다 한 줄씩 적는다. 호출 수 상한은 '한 번의 `--auto` 실행' 단위다 — 멈췄다가 재개하면 새 실행이다
- **실패 task** = 고치기 회차가 상한에 닿았거나 구현자가 BLOCKED 로 돌아온 task. 실패 task 는 '보류 처리'로 보류해 질문 모음에 올리고(`--skip`) **독립 task 는 계속한다**. 성공한 task 가 나오면 연속 실패 수는 0 으로 돌아간다. 연속 실패 수가 상한에 닿거나 호출 수가 상한에 닿으면 전부 멈춘다 — 멈춤 조건이다
- **관문 중 부하**: 전체 `python nova.py check` 가 도는 동안에는 새 구현자 · 무거운 배경 작업을 띄우지 않는다(읽기 전용 검토 · 자문 하나까지). 관문이 끝난 뒤 다음 묶음을 띄운다
- **멈출 때 보고**: ① 원장 첫 줄의 BASE 와 시작 브랜치 ② `git log --oneline <BASE>..HEAD` 의 커밋 목록 ③ 비파괴 되돌리기 안내 — 새 브랜치에서 `git switch -c <새 브랜치>` 뒤 `git revert --no-edit <BASE>..HEAD`(원래 브랜치는 그대로 남고, 병합 커밋이 끼어 있으면 revert 가 멈추니 그때는 보고만) **실행은 사람 확인 뒤에만** — 브랜치 삭제 · `reset` 은 안내하지 않는다 ④ 마지막 실패(task ID · 명령 · 출력 요지) ⑤ 체크된 task 와 남은 task ⑥ 질문 모음

### 재개
- 정본은 tasks 의 `- [x]` 와 git 기록이다. 원장(`.superpowers/sdd`)은 보조다 — 없거나 어긋나면 정본을 따르고, BASE 는 추측하지 않는다
- 끊긴 세션을 이어 가려면: ① `git status --porcelain` — 미커밋 변경이 있으면 멈춤 조건(반쯤 된 task 라 질문 모음) ② `/task-run <tasks_REQ_NN> subagent --auto` — '시작 전 점검'이 원장에 `재개` 줄을 덧붙인다 ③ `task_batch.py` 출력이 체크된 · 취소된 task 를 건너뛰고 열린 것만 낸다

### 병렬 위임
- 분석 · 조사 · 검토 요청은 배경 읽기 전용 에이전트에 맡기고, main 은 진행 중인 task 를 계속하며, 계획이 이미 정한 다음 task 는 사용자에게 묻지 않고 바로 간다.

## 하지 않는 것
- 에이전트가 에이전트를 부르게 하기(다층 호출) — 병렬은 main 이 한 층으로 직접 부른다
- 계획이 끝났다고 다음 계획으로 자동으로 넘어가기 — 끝나면 절차 8 에서 멈춘다
- 푸시 · 태그 자동화 — 사람 확인 뒤에만, 번호 기록 · 원장 · 커밋은 main 만
- `.claude/settings.json`(훅 · 허용 목록) 바꾸기
- 안전장치 상한을 넘겨 계속하기 · `--auto` 가 없는데 자동 진행 절을 적용하기
