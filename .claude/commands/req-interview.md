# /req-interview — 고객 인터뷰

인자: `$ARGUMENTS` (주제, 선택: 방식 A 실시간 · B 질문지 · C 회의록 분석)
규칙: [docs/conventions/superpowers.md §3](../../docs/conventions/superpowers.md)

## 절차
1. **스킬 호출**: `superpowers:brainstorming` 을 불러 대화 원칙을 따른다. 단 Nova 규칙이 우선한다:
   - 대화 · 기록은 한국어. 설계 문서는 `docs/superpowers/specs/` 가 아니라 아래 인터뷰 기록과 요구 문서에 쓴다
   - 이 명령은 **인터뷰까지**다. 요구 문서 · 승인 관문은 `/req-analyze` 에서 한다
2. `uv run python scripts/docs_new.py interview "<주제>"` → `docs/requirement/interviews/interview_YYMMDD_NN.md` + 인덱스. 인덱스의 `방식` 칸을 채운다(본 작업 트리에서 — 번호 기록은 main 이 만든 파일에 채운다)
2-0. **질문 전에 이미 있는 답을 읽는다**(빈손 인터뷰는 같은 것을 두 번 묻는다)
   - 체크리스트: `uv run python scripts/checklist.py import` — **최신 완료본(`status: complete`) 하나만** 발견(E-*) · 부족 항목(G-*)이 된다. 작성중은 반영하지 않고 "작성중 N건"으로만 알린다. 그 완료본의 md(`docs/warehouse/inbound/checklist/checklist_*.md`)를 읽되 **채운 칸은 답, 빈 칸 · "미정" 칸이 질문 재료**다. 체크리스트가 없는 것은 정상이다(결손으로 읽지 않는다)
   - 북극성: `docs/PROJECT.md` 가 채워져 있으면 읽는다(`/kickoff` 의 산출)
   - 기술 결정(언어 · 아키텍처 · DB · 횡단관심사 · 표준 판정)은 이 인터뷰에서 확정하지 않는다 — `/foundation` 몫이다
2-1. **부족한 것만 묻는다**: `docs/product/intake.json` 이 있으면 `uv run python scripts/warehouse.py gaps` 로 **근거 없는 영역 · 열린 부족 항목(G-*)** 을 질문 큐로 삼는다. 이미 자료로 답이 있는 것은 다시 묻지 않는다(되읽기로 확인만). 묻기 시작한 항목은 `status: "인터뷰 중"` + `interview: "INT-…"`, 답을 받으면 `status: "답함"` + `answer`(고객 말 그대로)로 바꾸고 `warehouse.py out`
3. 방식이 없으면 한 줄로 묻는다: "고객이 이 대화에서 직접 답하시나요, 직접 만나서 인터뷰하실 건가요, 회의록이 있으신가요?"
4. 방식별 진행
   - **A 실시간**: 첫 메시지는 "질문 없이 바로 시작하셔도 됩니다" 한 줄 + 실제 장면을 묻는 열린 질문 하나. 그다음부터 메시지마다 질문 하나. 답을 받을 때마다 §2 문답 기록에 원문 그대로 한 줄씩 추가한다. 한 영역을 이해하면 200~300자로 되읽고 §3 에 "확인/수정"을 남긴다. 화면 · 흐름 · 배치가 나오면 처음 한 번 시각 도우미를 따로 제안한다(`.superpowers/brainstorm/`, 커밋 안 함)
   - **B 질문지**: §3.1 영역별로 질문 3~5개(열린 → 장면 → 확인 순서), 고객 업종의 말로 §2 표에 쓰고 답 칸은 비운다. 사용자에게 질문지와 진행 요령(질문 하나씩, 답을 고치지 말고 받아 적기, "예를 들면요?"로 파고들기)을 준다. 인터뷰가 끝나면 답을 붙여 넣어 C 로 이어간다
   - **C 회의록 분석**: 붙여 넣은 원문을 §2 에 발언 그대로 옮기고(개인정보 · 비밀번호는 지움), §3 영역별로 정리한다. 영역이 비거나 발언끼리 부딪히면 §5 미결 질문으로 남긴다. 고객에게 다시 물을 질문 목록을 만든다
5. 고객이 말하지 않은 것은 §4 추측에 "Claude 판단"으로 둔다 — 고객 말로 쓰지 않는다
5-1. **요구 충돌**: 같은 쟁점이 질문 · 답 · 되읽기를 거쳐도 맴돌면(답이 뒤집히거나 두 발언이 부딪힌다) Claude 가 정하지 않는다 — §5 미결 질문에 "요구 충돌 — 고객 몫"으로 올리고 부딪히는 발언 두 개(§2 문답 #)를 함께 적는다. 임의의 가정으로 진행하지 않는다
5-2. **드러난 가정**: 인터뷰 중 드러난 숨은 가정(고객이 당연하게 여긴 전제 · Claude 가 세운 전제)을 기록 §4 아래 `### 4.1 드러난 가정` 절에 한 줄씩 남긴다 — `| 가정 | 드러난 곳(문답 #) | 확인됨 / 미확인 | 넘길 곳(요구 · /foundation · 미결 질문) |`. 미확인 가정은 `/req-analyze` 의 빌더 점검 재료가 된다
6. 끝내는 기준(§3.2): 영역마다 되읽기 확인이 끝나고, 남은 질문이 "고객 몫"뿐이면 상태를 `닫음`으로 바꾸고 §6 크기 판정을 쓴다
6-1. **교훈 후보**: 인터뷰에서 나온 교정(Claude 가 잘못 알아들어 고객이 고친 것) · 함정(다음 인터뷰에서도 놓치기 쉬운 질문)은 보고에 "교훈 후보"로 적는다. 교훈 원장은 강한 근거 식별자(REQ · ISS · history · review · ADR)가 필요하므로 `/req-analyze` 로 REQ 가 생긴 뒤 그 REQ 를 근거로 `/learn` 한다
7. `uv run python scripts/docs_index.py --check` → 사용자에게 인터뷰 요지(가장 중요한 것 3가지) · 요구 충돌 수 · 미확인 가정 수와 다음 단계를 알린다 — 입고 자료로 제품 전체를 정하는 중이면 `/prd`, 요청 하나를 정리하는 것이면 `/req-analyze INT-YYMMDD-NN`(이 명령은 승인 관문이 없다 — 요구 문서 · 승인은 거기서 한다)

## 하지 않는 것
- 수치 모호성 점수(psg05 Ambiguity ≤ 0.2)로 끝내기 — 끝내는 기준은 6(되읽기 확인 + 남은 것이 고객 몫뿐)이고, 검증은 `/req-analyze` 의 빌더 점검 · 승인 관문이다
- 요구 문서 · 계획 · 코드 쓰기 — `/req-analyze` 몫
