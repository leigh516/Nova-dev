# UI/UX 규칙 — 닐슨 10대 휴리스틱 + 보완 절차 (REQ-261103-02)

> 모든 화면(웹 · 모바일)은 이 규칙을 지킨다. 원칙을 "마음가짐"으로 두지 않고 **플랫폼 컴포넌트가 기본으로 해 주는 것**과 **화면을 만들 때 확인하는 것**으로 나눈다. 휴리스틱 평가의 단점(10개 틀 안에서만 보고 실제 사용자의 맥락을 놓침)은 §3 보완 절차로 메운다.

관련: [ui.md](ui.md)(토큰 → 컴포넌트 → 템플릿) · [design-system](../design-system/README.md)(WCAG 2.2 AA) · 계획서 §4 · 검토 템플릿

## 1. 10대 원칙 → 플랫폼 규칙

각 원칙마다 **[자동]** = 공통 컴포넌트 · 템플릿이 기본으로 처리(화면에서 따로 만들지 않는다), **[확인]** = 화면 작성자가 지키고 검토에서 확인한다.

### H1 · 시스템 상태의 가시성
- [자동] 데이터 화면은 템플릿이 **로딩(스켈레톤) · 빈 상태(EmptyState) · 오류(ErrorState + 다시 시도)** 를 그린다
- [자동] 서버 호출 버튼은 `useAction`(웹) / `rememberAction`(모바일): 진행 중 비활성 + 스피너, 성공 토스트, 실패 토스트
- [확인] 1초 넘는 작업은 진행 표시, 10초 넘으면 진행률 또는 단계 표시 + 취소 수단
- [확인] 저장 · 전송 결과는 항상 눈에 보이게(토스트 · 상태 배지 · 갱신된 목록). "아무 반응 없음" 금지
- [확인] 현재 위치 표시: 셸 메뉴 활성 표시, 페이지 제목(PageHeader), 필요 시 브레드크럼

### H2 · 현실 세계와의 일치
- [확인] 화면 문구는 사용자 말로. 내부 용어 · 코드값 · 테이블명 · enum 을 그대로 노출하지 않는다 → 상태는 `StatusBadge`(서버 설정의 이름 · 색)로
- [확인] 날짜 · 시간 · 금액 · 숫자는 공통 포맷 함수(`fmtAt`, 숫자 포맷)로 사용자 지역(locale · 시간대) 기준 표시
- [확인] 아이콘은 널리 알려진 의미로만 쓰고, 의미가 애매하면 글자를 같이 쓴다
- [확인] 용어집: 도메인 용어는 프로젝트 `docs/conventions/glossary.md` 에 한 번 정하고 화면 · API 설명이 같이 쓴다

### H3 · 사용자의 제어권과 자유도
- [자동] 되돌릴 수 없는 액션은 `useAction({confirm})` → 공통 확인 대화상자(`window.confirm/prompt` 금지)
- [확인] 되돌릴 수 있는 삭제 · 변경은 **실행 취소(undo) 토스트** 우선, 확인창은 정말 되돌릴 수 없을 때만
- [확인] 모든 대화상자 · 단계 화면에 닫기 · 취소 · 뒤로가 있다(ESC · 뒤로가기 동작 포함). 여러 단계 입력은 이전 단계로 돌아가도 입력이 남는다
- [확인] 작성 중인 입력을 잃는 이동(창 닫기 · 메뉴 이동)은 경고한다

### H4 · 일관성과 표준
- [자동] 색 · 간격 · 글꼴은 디자인 토큰만(`var(--color-…)`), 컴포넌트 API 는 `variant`(primary · secondary · ghost · danger) · `size`(sm · md · lg) 로 통일
- [자동] 같은 일을 하는 UI 는 같은 컴포넌트 — 두 번 나오면 공통 컴포넌트로 올린다(ui.md 규칙 2)
- [확인] 같은 행동은 같은 단어(예: "저장" 과 "등록" 을 섞지 않는다). 기본 문구는 컴포넌트 기본값을 쓴다
- [확인] 웹 · 모바일은 같은 이름 · 같은 흐름(DataTable ↔ DataList, PageHeader ↔ ScreenHeader)
- [확인] 플랫폼 관례(웹 링크 동작, 모바일 뒤로가기 · 하단 탭)를 깨지 않는다

### H5 · 에러 방지
- [자동] 폼은 입력 중 즉시 검증(필드 옆 메시지), 제출 버튼은 필수값이 채워지기 전 비활성 대신 **눌렀을 때 첫 오류 필드로 이동 + 설명**(이유를 알 수 있게)
- [자동] 중복 제출 방지(useAction 진행 중 비활성)
- [확인] 자유 입력보다 선택(드롭다운 · 날짜 선택기 · 자동완성), 입력 형식은 예시(placeholder)와 마스크로
- [확인] 위험한 버튼(삭제 · 결제 · 일괄 처리)은 `variant="danger"` 로 구분하고 일반 버튼과 떨어뜨린다. 영향 범위(몇 건)를 확인창에 숫자로 보여 준다
- [확인] 서버도 같은 검증을 한다(화면 검증은 편의, 서버 검증이 진실)

### H6 · 기억보다 인지
- [자동] 메뉴는 서버 메뉴(`/v1/menu`)와 셸이 항상 보여 준다
- [확인] 선택지는 화면에 보이게(드롭다운 · 칩 · 세그먼트), 최근 사용 · 즐겨찾기 · 기본값을 미리 채운다
- [확인] 다른 화면의 정보를 외워 오게 하지 않는다 — 필요한 맥락(선택한 항목 이름 · 이전 단계 요약)을 현재 화면에 다시 보여 준다
- [확인] 목록 검색 · 필터 상태는 URL 쿼리에 남겨 돌아와도 유지(`useQueryState`)

### H7 · 사용의 유연성과 효율성
- [자동] 목록 템플릿은 검색 · 정렬 · 필터 · 페이지 크기를 기본 제공, 표는 키보드 탐색 가능
- [확인] 자주 쓰는 작업에 단축키(웹: `/` 검색 포커스, `Esc` 닫기, `Ctrl+Enter` 제출 등 — 단축키 목록은 도움말(`?`)에서 보이게)
- [확인] 일괄 선택 · 일괄 처리, 최근 값 재사용, 딥링크(URL 로 바로 이동)
- [확인] 초보자 기본 흐름을 해치지 않는다 — 고급 기능은 숨기지 말고 한 단계 뒤에 둔다

### H8 · 미학적이고 미니멀한 디자인
- [확인] 화면마다 **핵심 행동 1개**(primary 버튼은 한 화면 한 영역에 하나)
- [확인] 지금 결정에 필요 없는 정보는 상세 · 접기 · 툴팁으로 내린다. 장식용 요소 금지
- [확인] 정보 위계는 토큰의 글꼴 크기 · 간격 단계만으로(임의 px 금지), 대비는 WCAG 2.2 AA(토큰 단계에서 자동 검사)
- [확인] 한 화면 너비는 `size.content` 토큰(narrow · default · wide) 중 하나

### H9 · 에러 인식 · 진단 · 복구
- [자동] API 오류는 `{error: {code, message}}` 봉투 → `ApiError.message` 를 사람 말로 보여 준다. 상태 코드(404 · 500)만 보여 주지 않는다
- [자동] 공통 `ErrorState`: 무엇이 잘못됐나 + 어떻게 하면 되나 + 다시 시도 버튼. 점검 중 · 권한 없음 · 네트워크 끊김은 각각 다른 문구
- [확인] 오류 메시지 3요소: **무엇이** 안 됐나 · **왜**(알 수 있으면) · **무엇을 하면** 되나. 사용자를 탓하는 말투 금지
- [확인] 실패해도 입력한 내용은 남긴다. 오류 필드에 포커스를 옮긴다
- [확인] 서버 오류 코드 → 문구 표는 서비스가 관리(`message`), 화면이 코드별 문구를 하드코딩하지 않는다

### H10 · 도움말 및 문서화
- [확인] 처음 보는 사용자가 막힐 만한 곳에 짧은 안내(빈 상태의 "처음이라면 이렇게" · 필드 도움말 · 툴팁)
- [확인] 앱마다 도움말 진입점(셸의 `?` 또는 도움말 메뉴) — 검색 가능한 도움말 · 단축키 목록 · 문의 경로
- [확인] 도움말은 작업 중심으로("~하려면"), 짧게, 화면 그림과 함께. 화면이 바뀌면 도움말도 같은 계획의 task 로 갱신

## 2. 심각도 등급 (닐슨 0~4)
| 등급 | 뜻 | 처리 |
|---|---|---|
| 4 | 치명 — 일을 끝낼 수 없음 | 출시 차단. 즉시 수정(P0) |
| 3 | 큼 — 자주 · 크게 방해 | 이번 계획 안에 수정(P1) |
| 2 | 보통 — 불편하지만 우회 가능 | 다음 계획 task(P2) |
| 1 | 미관 | 여유 있을 때 |
| 0 | 문제 아님 | 기록만 |

등급은 **빈도 × 영향 × 지속성(한 번 배우면 끝인가)** 으로 정한다.

## 3. 휴리스틱 평가의 단점을 메우는 보완 절차
| 단점 | 보완 | 언제 |
|---|---|---|
| 10개 틀 안에서만 문제를 찾는다 | ① **WCAG 2.2 AA 접근성 점검**(키보드만으로 조작 · 스크린리더 이름 · 대비 — 토큰 자동 검사 + 화면 점검) ② **과업 시나리오 점검**(인지적 워크스루: "사용자가 이 단계에서 무엇을 할지 알까? 했을 때 맞게 됐다고 알까?") ③ 도메인 특화 체크 항목을 프로젝트가 §4 체크리스트에 추가 | 계획서 §4 작성 시 · 구현 후 |
| 평가자 한 명의 시각에 치우친다 | 평가자 **2명 이상**(사람 + AI 검토 가능)이 따로 평가하고 합친다. 둘 이상이 같은 지적 = ★ 로 우선순위 올림 | 화면 검토 시 |
| 실제 사용자의 심리적 · 맥락적 문제를 놓친다 | ① **소규모 사용성 테스트**: 대표 사용자 5명, 핵심 과업 3~5개, 생각 말하기(think-aloud) — 성공률 · 걸린 시간 · 막힌 곳 기록 ② **실사용 데이터**: 오류율 · 이탈 단계 · 재시도 횟수 메트릭(공통 메트릭에 화면 이벤트 추가) ③ **피드백 경로**: 앱 안 의견 보내기 → 요구사항(REQ)으로 이어지게 | 주요 화면 출시 전(①), 출시 후 상시(②③) |
| 문제는 찾지만 고쳤는지 확인 안 함 | 지적마다 task 로 만들고, 고친 뒤 **같은 시나리오로 재평가**해 결과를 검토 문서 §3 에 남긴다 | 수정 후 |

> 원칙: **휴리스틱 평가 = 빠르고 싼 1차 거름망**, 사용성 테스트 · 실사용 데이터 = **진짜 문제 확인**. 하나만으로 끝내지 않는다.

## 4. 언제 무엇을 하나 (개발 흐름에 넣기)
| 시점 | 할 일 | 남기는 곳 |
|---|---|---|
| 세부 계획 §4 작성 | 목업으로 H1~H10 체크리스트 + 과업 시나리오 점검 | 계획서 §4 "UX 점검" 표 |
| 구현 PR | 아래 §5 체크리스트(자동 항목은 컴포넌트 사용 여부만 확인) | PR 설명 · 검토 문서 |
| 화면 묶음 완성 | 평가자 2명 휴리스틱 평가 + 심각도 등급 | `docs/reviews/review_YYMMDD_NN.md` |
| 주요 화면 출시 전 | 사용성 테스트(5명 · 과업 3~5개) | `docs/verification/` |
| 출시 후 | 오류율 · 이탈 메트릭 확인, 사용자 의견 → REQ | 대시보드 · requirement |

## 5. PR 체크리스트 (복사해서 쓴다)
```
UX (docs/conventions/ux-heuristics.md)
- [ ] H1 로딩·빈·오류 상태는 템플릿 사용 / 서버 호출 버튼은 useAction·rememberAction
- [ ] H2 내부 코드·용어 노출 없음, 날짜·숫자는 공통 포맷
- [ ] H3 취소·닫기·뒤로 있음, 되돌릴 수 없는 액션은 확인 대화상자, 가능하면 실행 취소
- [ ] H4 토큰·공통 컴포넌트만, 같은 행동 같은 단어, 웹·모바일 같은 이름
- [ ] H5 입력 즉시 검증, 선택형 입력 우선, 위험 버튼 danger + 영향 건수 표시
- [ ] H6 선택지·맥락이 화면에 보임, 필터 상태 URL 유지
- [ ] H7 검색·정렬·키보드, 필요한 단축키
- [ ] H8 핵심 행동 하나, 불필요한 정보 숨김, 토큰 간격·글꼴만
- [ ] H9 오류 문구 = 무엇이·왜·어떻게, 입력 보존
- [ ] H10 막힐 곳에 안내, 도움말 진입점
- [ ] 접근성: 키보드만으로 조작, 포커스 표시, 라벨·대체텍스트
```
