# 계획 문서 운영 규칙

계획은 세 층입니다. 위에서 아래로 갈수록 자세하고 자주 바뀝니다. **마스터플랜 → 세부 계획 → task** 순서로 만들고 진행합니다.

| 층 | 파일 | 담는 것 | 바뀌는 때 |
|---|---|---|---|
| 마스터플랜 | `master_plan.md` | 목표 · 구조 · 전체 순서 · 품질 게이트 | 중요한 결정이 생길 때 (초안 → 채택) |
| 세부 계획 | `plan_REQ_NN.md` | 한 요구의 설계(화면 · 데이터 · ERD)와 단계 | 단계 · 설계가 바뀔 때 |
| task | `tasks/tasks_REQ_NN.md` | 단계를 잘게 나눈 할 일 체크리스트 | 매 작업마다 (체크 · 추가) |

새 세부 계획과 task 파일은 함께 만든다: `uv run python scripts/docs_new.py plan "<제목>" --req REQ-YYMMDD-NN`
→ `plan_REQ_NN.md` + `tasks/tasks_REQ_NN.md` + `plan_index.md` 한 줄.

## 1. 마스터플랜 버전 관리 — 초안 → 정식
```
새 결정 발생 ──▶ drafts/master_plan_vX.Y-draft.md (상태: 초안)
                   │  확인: 사용자 결정(요구 · ADR)으로 확정? 링크 · 순서 맞음?
                   ▼
              채택 ──▶ 이전 정식본을 archive/master_plan_vX.(Y-1).md 로 보관
                       master_plan.md ← 초안 내용 (상태: 정식, 채택일)
                       master_plan_changelog.md 에 한 줄 기록 · 초안 파일 삭제(git 에 남음)
```
- **채택은 도구로 한다**: `python nova.py masterplan adopt drafts/<초안>.md --why "<근거 REQ · ADR>" --what "<바뀐 것>"`
  - 도구가 한 번에 하는 것: 지금 정본을 `archive/` 에 **봉인**(`archive/seals.json` 에 해시) → 초안을 정본으로(상태 정식 · 채택일 · 이전 정식 링크) → 이력 한 줄 → 초안 삭제
  - 손으로 옮기다 덮어쓰는 사고를 막는다. 이미 있는 봉인본은 덮어쓰지 않는다
- **지난 판본은 고치지 않는다**: `masterplan check`(lint)가 다음을 검사한다
  - 정본이 하나인가, 판본 번호가 이력과 같은가
  - 보관본이 봉인 그대로인가(바뀌면 실패), 초안이 정식을 자처하지 않는가
  - 첫 판본은 영구히 남는다 — "처음 무엇을 하려 했나"에 언제든 답한다(psg05 ADR-0065 · 0066 을 줄여 채택)
- **판본마다 끝이 있다**: 정본에 `## 종료 조건 (exit)` · `## 하지 않는 것 (이 판본)` 을 둔다. 조건이 모두 녹색이면 그 판본을 릴리스로 닫는다(§6)
- **버전 번호**: 큰 방향 전환(구조 · 릴리스 범위 변경) = 앞자리(v2.0), 계획 추가 · 순서 변경 = 뒷자리(v1.2)
- **초안을 만드는 경우**: 새 plan_REQ 추가, 서비스 구조 · 범위 · 순서 변경, 품질 게이트 변경. 오타 · 링크 · 체크 표시는 초안 없이 바로 고친다
- **채택 조건**: 내용이 사용자가 결정한 것(요구 문서 · ADR · 대화 답변)이어야 한다. 정하지 않은 내용이 있으면 사용자에게 묻고 나서 채택한다
- 초안이 있는 동안에도 작업은 정식본 기준으로 진행하고, 초안 맨 위에 "무엇이 바뀌는지" 표를 둔다
- 초안 안의 링크는 정식 위치(`docs/plans/`) 기준으로 쓴다 — 채택할 때 파일을 그대로 옮기면 된다

## 2. 세부 계획 버전
- `plan_REQ_NN.md` 맨 위 표에 `버전`, 맨 아래 `## 변경 이력`에 한 줄씩 (예: `v1.1 · 2026-11-03 · 2단계를 task 로 분해`)
- 마스터플랜 버전이 올라가 그 계획에 영향이 있으면 계획 버전도 올리고 "기준 마스터플랜 vX.Y"를 적는다
- 맨 위 표의 **추적 칸 다섯**(REQ-261105-04): `문서 ID` · `생성` · `위치` 는 `docs_new.py plan` 이 채우고, `원천` · `연결` 은 사람이 채운다(자리표시 그대로면 `docs_index.py --check` 실패 — 이 규칙 뒤에 만든 계획만). tasks 파일은 머리의 한 줄 표에 생성기가 다섯 칸을 모두 채운다

## 3. task 작성법 — 쉽게
- **한 줄 = 한 가지 일**. 동사로 끝낸다: "~ 만들기", "~ 옮기기", "~ 확인"
- **ID**: `T<계획번호>-<단계>.<순번 2자리>` (예: `T21-2.03`). 지운 task 의 ID 는 다시 쓰지 않는다
- **끝난 기준**을 괄호로 짧게: `(테스트 test_levels 통과)`, `(화면에서 보임)`
- 한 task 가 반나절이 넘을 것 같으면 둘로 나눈다
- **테스트는 단계 단위로 모은다**(REQ-261104-17): task 안에서는 그 테스트 하나만 RED → GREEN(몇 초). 끝난 기준에 테스트 경로를 적어 두면 단계 끝 **단계 관문** 한 줄이 `python nova.py quick --stage T<NN>-<단계>`(단계 테스트 + 바뀐 파일에 닿는 테스트 · lint, 느린 테스트 제외)와 전체 `python nova.py check` 한 번으로 묶어 확인한다. 커밋 · git 기록도 task 마다가 아니라 이 관문에서 묶는다
- 체크(`- [x]`)는 **코드 · 테스트로 확인한 뒤**에만. 뒤에 커밋이나 테스트 이름을 남기면 좋다
- 작업 중 새로 생긴 일은 그 단계 끝에 `🆕` 로 추가하고 같은 줄에 판정(`지금 — <깨는 종료 조건>` / `다음 판본`)을 적는다(plans README §5). 설계가 바뀌면 plan_REQ 에도 반영한다
- 하지 않기로 한 일은 지우지 말고 `~~취소선~~ — 이유` 로 남긴다

화면이 없는 계획(라이브러리 · 인프라)은 §4 를 "API · CLI 표면"으로 쓰고, 해당 없는 절은 `해당 없음 — 이유` 한 줄로 남긴다(절 번호는 지우지 않는다).

### 화면 미리보기 만드는 법
1. 지금 화면이 있으면 `docs/screenshots/` 의 캡처를 쓴다(없으면 dev 서버에서 찍는다)
2. 바뀐 뒤 화면은 `docs/plans/mockups/<REQ>/<앱>-<화면>.html` 에 **화면 본문만** 쓴다. 첫 줄:
   `<!-- mockup: {"app": "app|bare", "active": "/메뉴경로", "title": "…", "extra_links": [["/새메뉴", "이름", "아이콘"]]} -->`
   앱 셸(브랜드 · 메뉴)은 [`mockups/_shell.json`](mockups/_shell.json) 에서 정의한다
3. 클래스는 실제 웹 UI 것(`card` · `table` · `badge` · `seg` · `btn` …)만 쓴다 → 구현 화면과 모양이 같다. 새로 생기는 부분에 `class="mock-new"`(노란 점선)
4. `uv run python scripts/mockup_shots.py` → 같은 이름 `.png` 생성 → 계획서 §4 에 `![](mockups/<REQ>/<화면>.png)`
5. 구현이 끝나면 실제 화면을 같은 구도로 찍어 목업과 비교한다(task 로 둔다)

## 5. 목표 · 종료 조건 · 하지 않는 것 — 끝없이 넓어지지 않게
"하다 보니 하나 더"가 쌓여 일이 끝나지 않는 것을 막는다. 참조: project-start-guide-05 절대규칙 10 · ADR-0148 을 줄여 채택([ADR-008](../adr/ADR-008-parallel-bus-release.md)).
- **요구 · 계획 · 마스터플랜 판본 · 릴리스마다** 세 가지를 적는다
  - **목표**: 1~2문장(릴리스는 300자 안). 길면 목표 자체가 계속 자란다
  - **종료 조건(exit)**: `| ID | 확인 | 기대 | 방식 | 판정 |` 표, 1~7개. `명령`(실제로 돌려 종료 코드 0) 또는 `사람`(한 번 보고 '충족 YYYY-MM-DD')
  - **하지 않는 것**: 이번에 의도적으로 안 하는 것
- **종료 조건은 한 번 보거나 한 번 돌려 답이 나오는 것만**(재현형). "남은 결함을 전부 찾는다 · 없음을 증명한다" 같은 **소진형은 받지 않는다** — `goals.py` 가 **요구 문서와 릴리스의** 형식을 검사한다(계획서 · 마스터플랜 판본의 종료 조건은 사람이 확인한다 — 기계 검사 확장은 다음 판본 후보)
- **조건이 모두 녹색이면 끝이다**: `python nova.py exit-check REQ-…`. 끝난 요구는 상태를 완료로 바꾸고 닫는다
- **작업 중 새로 보인 것은 세 갈래 중 하나** — 기록에 처분을 함께 적는다
  1. 종료 조건을 깨는 것 → 지금 고친다
  2. 치명적인 것(보안 · 데이터 손실 · 장애) → 지금 고친다
  3. 그 밖 → 새 요구(`/req-new`) 또는 다음 릴리스의 하지 않는 것 · backlog 로 보낸다. **이번 일을 넓히지 않는다**
- **개선이 개선을 낳지 않게** (REQ-261105-03 — 리뷰 · 감사 · 교훈 · 작업 중 발견에 똑같이 적용)
  1. **고치기 전에 셋을 먼저 적는다**: 리뷰 · 감사 결과로 고칠 것은 기존 요구에 붙이거나 새 요구로 만들어 **목표 · 완료(종료) 조건 · 하지 않는 것**을 적은 뒤 착수한다. 적지 않은 개선은 시작하지 않는다
  2. **🆕 의 기본 행선지는 '다음 판본'**: 지금 고치는 것은 위 1 · 2(지금 일의 종료 조건을 깸 · 치명)뿐이다. "작으니까 지금"은 이유가 되지 않는다. 🆕 줄에 판정(`지금 — E2 를 깸` / `다음 판본`)을 함께 적는다
  3. **한 세대 규칙**: 개선 작업(리뷰 반영 · 감사 처분 · 교훈 반영 · 훅 · 게이트 보강)에서 새로 보인 것은 **같은 회차에 다시 고치지 않는다** — 다음 판본 목록에만 적는다
  4. **플랫폼 개선 동결**(REQ-261105-10-6): [REQ-261105-09](../requirement/requirement_261105_09.md)(자동 진행) · [REQ-261105-10](../requirement/requirement_261105_10.md)(개발 속도)이 끝나면, 플랫폼 자체를 고치는 새 요구는 **실제 제품 개발에서 드러난 결함 · 마찰**만 받는다 — 요구 문서 '원천' 칸에 그 제품 개발의 근거(제품 저장소 · 요구 · task 또는 결함 ID)를 적는다. 예외: 결함 원장(`docs/issues/`)의 결함 · 검사 신뢰(🆕 T08-9.01 하위 프로세스 비정상 종료 같은 것) · 보안

## 6. 병렬 개발 · 메시지 버스 · 릴리스
**속도를 위해 병렬로 가되, 공통 영역이 끝나기 전에는 갈라지지 않는다.** 결정: [ADR-008](../adr/ADR-008-parallel-bus-release.md)
```
마스터플랜 '## 공통 영역 완료 선언' 모두 완료(+증거) · '## 병렬 묶음' 2개 이상 · 경로 겹침 없음
   │ python nova.py parallel-gate                (닫혀 있으면 직렬로 간다)
   ▼
python nova.py worktree-new <묶음>  ×N           .worktrees/wt-<묶음> · 브랜치 wt-<묶음> · 버스로 인계 카드
   │ 각 worktree: 자기 경로만 · 종료 조건이 녹색이면 끝 · 질문 · 보고는 버스(send · inbox · done)
   ▼
python nova.py converge <묶음> --verify (main)    병합 → test · lint → main 에서 이력 · git 기록(단일 기록자)
   ▼
python nova.py release ship <버전>               판본 종료 조건 실제 판정 → 태그 · 노트 → 다음 draft
```
- **단일 기록자**: 번호가 붙는 기록(요구 · 계획 · 이력 · git 기록 · 세션 · ADR · 리뷰)과 인덱스는 **본 작업 트리(main)만** 쓴다. worktree 에서는 도구가 거부한다 — 두 브랜치가 같은 번호를 만들면 병합 때 반드시 충돌하기 때문이다
- **메시지 버스**: 본 작업 트리의 `.collab/` 하나(커밋 안 함)
  - 보낸 메시지는 고치지 않는다 — 회신은 `--reply-to` 로 새 메시지
  - 한 주제로 3번 넘게 오가면 `escalation` 으로 main(사람)에게 넘긴다
  - 끝낼 때는 반드시 `--result`(무엇이 됐나)
- **공통 영역 = 모든 개발이 같은 것을 쓰게 하는 표준 · 공통 모듈.** 필수 7항목: CI(test · lint 녹색) · 인증 · 권한 한 경로 · DB · 마이그레이션 · 서비스 사이 계약(API · 이벤트) · **화면 공통 모듈**(화면 틀 · 디자인 토큰 · 공통 UI 부품 · 템플릿) · **공통 컴포넌트**(라이브러리 — `nova_common` · `@nova/sdk` · `kr.nova.shared`) · **공통 명명 규약 · 개념 원장**. 상태는 완료 · 진행 · 미해당, 완료에는 증거(테스트 · 커밋 · 문서)
- **왜 먼저인가**: 공통 모듈이 끝나기 전에 갈라지면 worktree 마다 화면 구성 · 부품 · 이름을 따로 만들어 통일성이 깨지고, 수렴(`/converge`) 때 한꺼번에 터진다. 그래서 7항목은 판본 검사가 **필수로 본다** — 표에서 줄을 지워 게이트를 열 수 없다(`scripts/masterplan.py` REQUIRED_COMMON). `/dispatch` · `/worktree-new` 는 게이트 단계에서 `python nova.py parallel-gate` 를 부른다
- **릴리스**: `docs/releases/releases.json`(판본마다 목표 · 종료 조건 · 하지 않는 것 · 묶인 요구 · 담는 마스터플랜 판본)과 노트 `docs/releases/v<버전>.md`(복제본이 받을 때 · 되돌리기 절 필수). draft 는 한 번에 하나. 태그를 원격에 올리는 것은 사람 확인 뒤. 번호 올리기 · 사전 판본 · 마스터플랜 1 : 릴리스 N · 템플릿 = 최신 정식본은 [판본 규약](../conventions/versioning.md)이 정본이다
