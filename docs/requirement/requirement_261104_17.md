## 의도 (INTENT — 해법을 적기 전에)
"누가 왜 곤란한가"를 해법보다 먼저 적는다. 이것이 이미 해법을 담고 있으면 문제 진술이 아니다. `미해결` 은 비우지 않는다(없으면 "없음") — `docs_index --check` 가 검사한다.

| 칸 | 내용 |
|---|---|
| 문제 | Nova 로 개발하는 사람이 task 마다 전체 test(이 PC 12~16분) · lint(2~3분)를 돌리고 작은 일에도 큰 절차를 밟아, 표준화가 목적과 달리 개발 속도를 떨어뜨린다. 2주 이하 작은 프로그램에도 체크리스트 → PRD → SPEC → 마스터플랜 착수 절차가 무겁다 |
| 결과 | task 마다는 바뀐 곳에 닿는 빠른 검사만, 단계 끝 · 푸시 묶음에 전체 검사. 기록은 크기에 맞게, git 기록은 푸시 묶음마다. 프로젝트 규모 프로파일(lite · product · platform)이 착수 절차 · 기록 하한 · 검사 단의 기본값을 정하고, 되돌리기 어려운 일은 어느 프로파일이든 [DEEP] 으로 올린다 |
| 영향 | nova.py · task-run · finish · history-new · docs-write · sdd · kickoff · test · git-save · CLAUDE.md 문서 규칙 4 · superpowers.md §4 · nova.project.json profile · new_project · parallel 게이트 |
| 제약 | 승인 관문 · 안전 검사(비밀값 · 토큰 대비 · 생성물 --check · 표준 판정 · 한국어)는 어느 프로파일에서도 빼지 않는다 · 기록 하한(커밋 + git 기록)은 면제하지 않는다 · SOUL/STYLE 은 바꾸지 않는다 |
| 미해결 | 없음 — 화면 수 · 서비스 수 문턱값은 Claude 판단으로 시작하고 실측으로 고친다 |

## 목적과 이유
ERP 실개발 추정에서 절차 부담은 5~10% 지만 검사 실행이 task 마다면 20~30% 를 차지함이 드러났다(이 PC 실측). 사용자는 공통개발플랫폼의 목적(신속성 · 효율성 · 정확성)을 해치지 않게 보정하라고 했다.
