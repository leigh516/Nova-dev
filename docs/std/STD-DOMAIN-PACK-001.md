# STD-DOMAIN-PACK-001 — 코어 · 도메인 팩 분리 표준

> **한 줄 요약:** "다음 고객 · 다음 업종에 재출시"를 **개발이 아니라 구성**으로 만드는 구조다. 공통은 코어에, 업종 특성은 팩에 두고, **분리를 문서가 아니라 폴더와 의존 방향으로 강제**한다.

- 상태: 표준(판정 의무) · 출처: project-start-guide-05 STD-DOMAIN-PACK-001 → Nova 구조로 다시 씀
- 적용 대상: **같은 제품을 여러 업종 · 고객군에 파는** 프로젝트. 단일 도메인 제품이면 **면제**(판정 기록) — 두 번째 업종이 실제로 보일 때 도입해도 늦지 않다

## 비유 — 자동차 플랫폼
| 자동차 | Nova |
|---|---|
| 플랫폼(섀시 · 파워트레인) | **플랫폼** `packages/common-py`(nova_common) · 게이트웨이 · 인프라 |
| 차종 공통 차체 | **코어** `services/<서비스>` — 어느 업종에나 참인 업무 로직 |
| 차종별 외장 · 튜닝 | **도메인 팩** `packs/<팩>/` |
| "플랫폼에 차종 전용 부품 용접 금지" | 코어에 업종 분기(`if domain == "pharma"`) 금지 → **포트**로 |

**창고관리로 보면**: 입출고 · 재고 · 로케이션 · 작업지시는 어느 창고나 같다(코어). 신선식품의 유통기한 · 선입선출과 의약품의 로트 추적 · 시리얼 · 감사증적은 튜닝이다(팩). 의약품 고객이 오면 **코어는 그대로 두고 팩만 만든다**.

## 3원칙
1. **공통성/가변성으로 가른다** — 어느 업종에나 참인 것만 코어. 애매하면 팩에(팩 → 코어 승격이 반대보다 싸다)
2. **분리는 폴더와 의존 방향으로 강제** — `scripts/packs.py check` 가 lint 에서 검사
3. **도메인 지식은 코드가 아니라 데이터 · 설정 · 포트 구현** — 새 업종 진입 때 *고쳐야 하는 코어 코드의 양*이 이식 비용이다

## Nova 구조
```
packages/common-py/        플랫폼 — 테넌시 · 인증/권한 · 이벤트 · 팩 로더(nova_common.packs)
services/<서비스>/<패키지>/  코어 — 업무 로직 + 가변점 선언 @packs.port("<패키지>.<포트>")
packs/<팩>/                도메인 팩
  pack.json                이름 · 설명 · extends(확장하는 서비스) · 가변점
  glossary.md              ① 용어 오버레이
  schema/<패키지>.py       ② 확장 표 <팩>_<개체>_ext (코어 표에 컬럼 추가 금지)
  policies/<패키지>.py     ③ 포트 구현 @implement("<패키지>.<포트>")
  screens.json             ④ 화면 오버레이(추가 컬럼 · 라벨 · 탭)
  workflows/*.json         ⑤ 프로세스 정의(단계 · 승인)
```
**의존 규칙(단방향)**: `packs → services(코어) → packages(플랫폼)`. 코어가 `packs` 를 import 하면 lint 실패, 팩끼리 import 해도 실패.
**켜기**: `nova.project.json` `"packs": ["pharma"]` → 생성기가 `NOVA_PACKS` 를 ConfigMap · compose · 개발 서버에 넣고, 서비스가 기동 때 `packs/<팩>/policies/<패키지>.py` 를 불러온다. 켜진 팩이 없으면 **기동 실패**(업종 규칙이 빠진 채 운영되지 않게).

## 가변점 5종
| 가변점 | 코어가 제공 | 팩이 채우는 것 | Nova 상태 |
|---|---|---|---|
| ① 용어 | 코어 용어(`docs/conventions/glossary.md`) | `glossary.md` 오버레이 | ✅ 파일 규약 |
| ② 데이터 | 코어 표 + 확장 포인트 | 확장 표 `{팩}_{개체}_ext`(같은 서비스 DB, 코어 표 FK 는 `ref_column`) | 🗺 규약 — 첫 사용 프로젝트가 예시를 역제안 |
| ③ 규칙 | `@packs.port` 기본 구현 | `@implement` 구현 | ✅ `nova_common.packs` · 예시 `packs/example` |
| ④ 화면 | 코어 화면 + 슬롯 · 컬럼 설정 | `screens.json` | 🗺 규약(웹 앱이 읽어 적용하는 구현은 첫 사용 시) |
| ⑤ 프로세스 | 워크플로 엔진(상태기계) | `workflows/*.json` | 🗺 규약 |

## 금지 3조 — 코어 오염 방지
1. **코어에 업종 분기 금지** — `if pack == …` 를 쓰지 않는다. **분기가 필요한 자리가 곧 포트 후보**다
2. **팩끼리 직접 의존 금지** — 공통이 필요하면 코어 승격 절차로(lint 가 import 를 잡는다)
3. **코어 표에 업종 전용 컬럼 금지** — 확장 표로 뺀다([DB 사전](../registry/db-dictionary.md)에서 리뷰)

## 새 업종 착수 절차
```
1) 갭 분석: 새 요구를 3분류 — [코어로 충분 | 포트로 흡수 | 코어 승격 후보(두 업종 이상에서 반복)]
   → 세부 계획서 §2 모델 변경 표에 분류를 적는다
2) python nova.py new-pack <팩> --title "<이름>" --extends <서비스>
3) 용어 오버레이부터 — glossary.md 가 팩의 첫 산출물
4) 가변점 ②~⑤ 채우기 — 코어 파일은 원칙적으로 고치지 않는다
5) 코어 수정이 불가피하면: "포트 추가" 요구(REQ) → 계획 → 마스터플랜 초안 —
   특정 업종 로직이 아니라 **소켓(포트)을 늘리는 방향으로만**. 이것이 플랫폼이 진화하는 유일한 경로다
6) nova.project.json packs 에 추가 → python nova.py test · lint
```
> **두 번째 업종에서 이식 비용을 실측해 history 에 기록한다**(고친 코어 파일 수 · 새 포트 수 · 걸린 시간). 그 숫자가 이 구조의 효용을 증명하거나 반증한다.

## 도메인 에이전트 (팩과 짝 — ADR-009)
팩마다 그 업종의 업무를 아는 읽기 전용 판정자 `<팩>-specialist` 를 하나 둔다(`.claude/agents/domain/`). 팩을 만들면 함께 생기고(`python nova.py new-pack`), 지식은 팩에서 읽는다 — 에이전트 정의에 업무 규칙을 베끼지 않는다. 팩이 없어지면 에이전트도 지운다(lint 가 짝을 검사한다). **팩이 없는 업종 지식 에이전트는 만들지 않는다** — 업종 지식은 팩에 두고 에이전트는 그것을 읽는다. 자세히: `packs/README.md` '도메인 에이전트'.
