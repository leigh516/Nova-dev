# ADR-003 · 식별자는 UUID version 7

| 항목 | 내용 |
|---|---|
| 일자 | 2026-11-03 |
| 상태 | 채택 |
| 대체 | - (dayroom2 의 ULID · 접두어 ID 를 대신) |
| 요구 | [REQ-261103-06](../requirement/requirement_261103_06.md) |

## 배경
dayroom2 는 26자 ULID 와 사람이 읽는 접두어 ID(`RV-01J…`)를 섞어 썼다. 표준이 아니어서 DB · 언어 · 도구 지원이 약하고, 접두어는 개체 이름이 바뀌면 낡는다. 사용자는 최신 표준인 UUID version 7 을 요구했다.

## 결정
- **DB 기본키 · 다른 개체를 가리키는 칸 · 이벤트 ID 는 UUIDv7**(RFC 9562 §5.7)
- 저장 형식: **CHAR(36) 소문자 문자열**(`nova_common.ids.id_column()` · `ref_column()`). v7 은 앞 48비트가 밀리초 시각이라 문자열 사전순 = 생성 순서
- 생성: `nova_common.ids.new_id()` — RFC 9562 §6.2 방법 1(12비트 전용 카운터)로 같은 밀리초 안에서도 프로세스 내 엄격 증가. Python 3.12 에 `uuid.uuid7` 이 없어 직접 구현(3.14 표준 함수와 같은 형식)
- 접두어 ID 금지. 사람이 읽는 업무 코드(주문번호 · 사번)가 필요하면 **별도 칸**(`code`)으로 두고 UNIQUE
- 생성 시각이 필요하면 `uuid7_time(id)` — 단, 업무 시각은 `created_at` 칸이 정본(ID 시각은 보조)

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|
| UUIDv4 | 어디서나 지원 | 무작위 → B-tree 페이지 분할 · 인덱스 단편화, 정렬 불가 | 삽입 성능 · 정렬 |
| ULID | 시간순 · 짧음(26자) | 비표준, DB 네이티브 타입 없음 | 표준 v7 이 같은 장점 |
| 자동 증가 정수 | 작고 빠름 | 서비스 · 오프라인 생성 불가, 개수 노출, 병합 충돌 | MSA · 이벤트에 부적합 |
| 네이티브 UUID 타입(BINARY(16) · PostgreSQL uuid · MariaDB UUID) | 저장 공간 절반 | 엔진마다 다르고 SQLite 미지원, 사람이 읽기 어려움 | 이식성 우선 — 대용량 표는 프로젝트 ADR 로 바꿀 수 있다 |

## 결과
- 좋아지는 것: 표준 형식, 시간순 인덱스 삽입, 분산 생성, 이벤트 · DB 같은 ID 체계
- 감수하는 것: CHAR(36) 은 BINARY(16) 보다 크다
- 이후 규칙: 새 표의 기본키는 반드시 `id_column()`. 리뷰에서 `String(...) primary_key` 직접 선언은 지적한다
